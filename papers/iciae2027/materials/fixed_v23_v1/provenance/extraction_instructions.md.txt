# 研究室PCで執筆資料をGit共有するための実行プロンプト

作成日: 2026年11月4日。以下を研究室PC側の会話に渡して実行する。
このファイルは実行指示であり、資料の書出し・共有が完了した記録ではない。
目的は、ノートPCがGitから取得した資料だけで既存Main/Calの本文・図表・具体例を確認して執筆できる状態を作ること。
著者情報の本人確認、関連研究本文の精読、教員確認、論文提出は別工程である。

---

ノートPCでICIAE 2027向けの論文を執筆しています。研究室PCにある固定v23 Main/Calの既存成果から、
執筆に必要な資料を作成・検証し、GitHubへCommit・通常Pushしてください。
単なる所在メモではなく、ノートPC側で質問・実使用根拠・回答・順序別判断・品質・費用を追跡できる資料集を完成させてください。

## 1 今回の許可範囲と成果の保全

- この依頼は、既存Main/Calの選定済み80 QAに限った執筆用の派生資料・具体例を、後述の専用フォルダへ格納してGit共有する指示です。
- その範囲で必要な質問、Reference、実使用根拠、初回/書換え回答、確定済み評価・採点の共有を許可します。
  以前の「回答/根拠全文をGitへ追加しない」「Git外で資料転送」の指定は、この専用の検証済み執筆資料に限り本指示で置き換えます。
  元Raw/Run全体、全Corpus、未使用QA、モデル、Index、環境を丸ごと公開する指示ではありません。
- 元Run・元設定・全採点封印は読み取り専用とし、元ファイルを上書き・再生成しないでください。
- 新規推論、Codex CLIによる再採点、閾値/Prompt/モデル変更、失敗QAの補充、未知の補完は行わないでください。
- 進行中の追加実験やサービスを停止・変更せず、それが参照するCheckoutへPullしないでください。
- 未使用Evaluation、追加検証の未封印資料、認証情報・秘密鍵・個人の認証設定を含めないでください。
- 出典・Revision・元データの利用条件・必要な帰属表示を、既存の取得記録/NOTICEと照合して同梱してください。
  共有条件を満たせない原文は黙って書き換えず、未共有項目と固定版の取得手順/位置/Hashを明記し、共有可能な資料は先に完成させてください。

## 2 安全なGit作業場所

1. AGENTS.md、最新の研究計画・実装計画・ロードマップを確認し、Git状態・Branch/Commit・remote・追跡先・実行中Runの参照Checkoutを調べてください。
2. originをFetchして履歴差分を確認し、未コミット変更や実行中Checkoutを保全してください。
3. 執筆Branchは origin/paper/iciae2027 です。このBranch上の次の文書を読み取りで確認してください。
   - papers/iciae2027/README.md
   - papers/iciae2027/manuscript/outline.md
   - papers/iciae2027/notes/case_studies_and_materials.md
   現在の作業場所へPullできなければgit showで読み、別のWorktreeを使ってください。
4. 最新origin/paper/iciae2027を起点に、実験から独立した資料共有Worktree/Branchを作ってください。
   Branch名は paper/iciae2027-materials-v1 を基本とし、既存なら履歴と用途を調べ、上書きせず継続または別名にしてください。
5. 変更は新しい資料フォルダと、その案内・検証に必要な最小範囲へ限定してください。mainや元実験Checkoutを変更しないでください。

## 4 作成するGit共有資料

出力先は papers/iciae2027/materials/fixed_v23_v1/ とします。
既に資料が存在する場合はHashと生成条件を確認し、同一物は再利用、異なる結果は別Versionへ保存してください。
以下は必要な内容であり、ファイル分割は読みやすさ・サイズに応じて調整できます。変更した場合はREADMEで案内してください。

| 資料 | 必須内容 |
|---|---|
| README.md | 資料索引、各章で使う資料、対象/分母、参照方法、検証コマンド、取得不足、共有の完了状態 |
| experiment_conditions.md | Dataset/分割/選定、モデル/量子化/Prompt/閾値/試行/予算/Runtime、採点基準と各集合の役割 |
| results_explanation.md | 主増分・区間・日英差・品質遷移・方策品質・費用・意味監査・閾値感度の読み方と元表の対応 |
| limitations_and_deviations.md | 欠測、判定不能、事後停止規則変更、採点方式差、AI採点、人手未確認、外的中断の費用不明等 |
| annotation_provenance.md | Rubric/Prompt/Schema、実採点モデル識別の取得可否、日時、遮蔽した情報、履歴分離の限界、形式修正の履歴 |
| references_and_attributions.md | Dataset/モデル/根拠のSource URL・固定版・利用条件・帰属/変更表示、引用候補の書誌/URL・確認範囲 |
| qa_summary.csv | 全選定80 QAの集合/言語/ID/Group、生成・書換え・比較可能状態、欠測理由、A/B品質、主増分等 |
| trials.jsonl | 全予定順序/反復のQA対応、実提示ID列、F、判断/Action、状態、固定文Label・根拠・費用、再利用/重複順列の扱い |
| policy_outcomes.csv | QA別・方策別の選択A/B、品質、書換え要求/Fallback、改善見逃し/悪化、Call/Token/既知時間 |
| inputs/ | 選定済みQAの質問・Reference/Goldと、実使用根拠全文/Title/ID/URL/Hash・A/B・固定文・日本語参照来歴。QA別に保存可能 |
| annotations/ | 確定済み品質/Expected、理由・引用、匿名候補と元QA/段階の対応。再採点せず原記録へ追跡できる形 |
| cases/ | 原文・順序・F/判断・A/B・Y・根拠を照合した具体例2～4件程度と、元ファイルの位置/Hash・選定方法 |
| analysis/ | QA別統計・Group情報・元詳細解析から必要な項目。公開集計の生成元を追跡する情報 |
| published_results/ | 既存公開集計・図表・成果Manifestの同一バイト複製。元の公開値との照合を資料内で完結させる |
| provenance/ | 元Manifest/採点封印/条件・採点来歴等の必要な複製、元ファイルとの対応とHash |
| source_manifest.json | 元Repository/Commit/Release、Run、各入力ファイルの元パス・SHA-256、80 QA/全候補との対応 |
| artifact_manifest.json | 共有ファイルの相対パス・バイト数・SHA-256。自己参照を除いた全成果を列挙 |
| verify_materials.py | 標準ライブラリ中心で、資料内の欠落・Hash・対応・件数・指標を検査するノートPC用の検証入口 |

元Run全体や巨大ログをそのままコピーする代わりに、本文・図表・実例の確認に必要な確定情報を抽出してください。
元ファイルの完全複製と抽出/整形したファイルを区別し、後者には元の位置・Hashと変換内容を記録してください。
Word原稿に使う根拠抜粋と、その確認用の実使用根拠全文を区別してください。
採点基準・Prompt・Schema・実験条件は版名だけで済ませず、必要な本文/設定も同梱してください。
抽出・集計処理のコードと実行コマンドも保存し、出力がどの入力・処理から得られたかを追跡可能にしてください。

## 5 内容を欠落させないための条件

- 失敗・拒否・固定文なし・評価不能を除外せず、全選定80 QAの実施状況を残してください。
- 同一候補の採点共用や、初回/書換えが同じ文章の場合の対応を保持してください。80×2個の独立候補を仮定しないでください。
- 重複順列の省略、存在しないTrial、初回生成失敗、評価不能、書換え失敗Fallback、外部品質の判定不能を区別してください。
- 不明なYや費用を0へ変換せず、null/状態/理由を保持してください。Fを正答率として扱わないでください。
- 固定文数・Label・引用からFを照合し、閾値・Action・選択候補・外部採点Yと経路費用をQA内で対応付けてください。
- Main/Cal・日英を分け、全対象と完全比較の分母を保持してください。文・ペア・Callを独立QAと数えないでください。
- 公開CSVの列名や欠測ラベルに曖昧さがあれば元Runと照合し、旧成果を書換えず差異・理由を別記してください。
- 具体例は可能なら日英から選び、結果閲覧後の説明例であることと選定規則を記録してください。
  「判断も品質も変わる」「判断は変わるが品質は同じ」等は、存在を確認できた例だけを使い、見つからない型を作らないでください。
- DatasetのReference/Goldと、実際に通常検索で使った根拠を分け、推論へ正解を渡したような図を作らないでください。
- 読取用に原文を整形/抜粋した場合も元の全文・位置・Hashへ戻れるようにし、意味や数値を変えないでください。
- 著者名・所属や、未取得のモデルID・未精読文献の内容を推測で埋めないでください。

## 6 検証とノートPCでの自己完結性

1. 元成果の科学的記録・全採点封印・Source Hashを抽出前後に照合し、変更0を確認してください。
2. 主比較、比較可能数、品質・費用、意味監査を既存公開CSV/JSONと照合してください。
   差異があれば原因を調べ、元成果は保持して注記し、未解決の値を正しいと認定しないでください。
3. 資料だけでQA別のO/R/D、判断反転、品質遷移、改善見逃し/悪化、方策集計等を再確認できるようにしてください。
   Bootstrapの区間は実装Version/NumPy Version/Seed/反復数と元結果を保持し、別実装の値を同一と偽らないでください。
4. ノート用検証は、資料フォルダ内の相対パスだけで動き、元Runの絶対パス・GPU・モデル・Index・認証・ネットワークを要求しない形にしてください。
5. CSV/JSON/MarkdownをUTF-8で保存し、専用フォルダ内に限定したGit属性等でWindows/Linux間のバイト変換を防いでください。
6. 検証コードには欠落/改ざんの拒否、ID・候補・段階対応と欠測の扱いなど必要な確認を行ってください。
   Python処理はuvで実行し、コードを追加した場合は変更に応じたpytest/Ruffも実施してください。
7. Gitに載せた内容から新しい一時Checkout/Archiveを作り、元Runを読まない検証を実行してください。
   全ファイルHash、全選定80 QA、両言語、必要な候補/Trial/採点対応、具体例の根拠、相対リンクを検査してください。
8. 必須資料が不足する場合は、取得できたものをPushし、足りない項目・理由・必要な操作を明示してください。
   必須情報が欠けたまま「ノートPCで執筆資料が全てそろった」と報告しないでください。

## 7 CommitとPush、執筆Branchへの反映

差分と対象を確認し、今回の執筆資料・抽出/検証用の必要ファイルだけをCommitし、資料共有Branchへ通常Pushしてください。
force push、履歴上書き、他の未完成変更の混入、元Runをgit add -fで丸ごと追加することは禁止です。

Push前に再Fetchし、origin/paper/iciae2027が作業開始時の基点から変わっておらず、資料Commitへ早送り可能であれば、
同じCommitを執筆Branch paper/iciae2027にも通常Pushして反映してください。
執筆Branchが進んでいた場合は自動Merge/Rebaseや上書きをせず、共有Branchを保持し、ノート側へ取込元Branch/Commitを報告してください。
Push後はリモート先端とローカルCommitの一致を確認し、PushしたCommitの新しい取得コピーでも検証してください。

## 8 終了報告に必ず含めるもの

- 保存先・成果索引・資料内の参照方法とノートPC用検証コマンド。
- 全選定80 QA/4区分と、欠測・Trial・候補・採点・方策の対応状況。
- 採用した具体例のID/由来/選定理由と、原文/F/判断/Y/費用の確認状況。
- 元成果不変、新規推論0、再採点0、検証結果、公開集計との一致/差異。
- 共有した原文の出典・利用条件・帰属表示、未共有/不足項目と理由。
- Commit ID・日本語Commit文・PushしたBranch・リモート一致・未コミット/未Pushの有無。
- 「ノートPCのCodexへ渡す引継ぎ文」: 取込元Branch/Commit、資料パス、検証コマンド、残件を、そのまま貼れる一文または短文で示す。
  ノート側でもGit状態・Fetch後の履歴差分を確認し、変更を保全して安全に取り込む指示を含めてください。
- 最後に、実験資料についてノートPC単独で確認できる状態になったかを、検証結果に基づき明示してください。
