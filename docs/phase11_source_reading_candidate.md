# Phase 11 草稿を見ない根拠読解を先行する候補の事前計画

作成: 2026年10月21日。共同評価の3候補と固定文候補がCouncilの誤帰属を通過しなかったための次案。
既存の不通過・未試行・Expected・採用基準を保持する。現段階では計画のみで、実装/Model実走していない。

## 変更の理由と範囲

全4候補は、Pius Vの本文が実Promptに存在していてもCouncilへ行為を帰属した。
新候補では、内部Judgeの最初の段階に質問と全根拠だけを渡し、誤った草稿/Claimを見せずに主体・行為・原文箇所を抽出する。
次段階は固定文候補と同じ全固定文を評価するが、最初の読解結果を検証対象の補助情報として明示する。
補助情報を正解や追加検索根拠とはせず、元の全根拠本文/ID/Titleも省略せずに渡す。

- 読解段階の入力は質問と全実使用文書だけ。初回回答・固定文・Expected/Reference/Labelを渡さない。
- 各文書について少なくとも1件の主体/行為と完全一致の原文箇所を返す。引用は実文書と照合し、全文書IDを覆う。
  字面の一致は意味の正しさの保証ではなく、読解結果の意味も監査する。
- 出力SchemaのID集合は順序によらず同一にする。元根拠の順序を並べ替えたり、読解結果を外部で都合よく正解へ修正しない。
- 読解結果は各試行で実生成し、同一順序反復の結果Cacheにしない。同じ試行内の全固定文には共通結果を使う。
- Judge内部が複数段階になる変更で、根拠順序に依存する読解結果は中間出力として保存する。
  質問/初回回答/固定文/元本文を変えず、介入は元根拠配列の提示順だけとする。
- 固定文の全分母・閾値0.7/9判断・5反復・Seed/再試行0・書換え1回・品質基準を維持する。
  読解または1固定文でも失敗した試行のFはnull、全実Call/Token/時間を費用へ含める。

## 事前の実行条件と採用規則

同じ8B/CUDA/Context12288/Seed42を候補にする。読解は出力予約4096/推論1536、固定文検証は3072/1536を初期予算にする。
Samplingは現候補と同じ。読解後の実Tokenで入力予算を検査し、超過は切詰めずに保存して停止する。
長時間実走は検証済みCommitの専用Worktree。先にSource/Config/Expected・全予算・停止規則をManifestへ保存する。

既知Council全7文/Zidane1文の元/逆は、読解4+固定文16=最大20 Completionを先行する。
Critical4条件の正確Label全一致・形式/Runtime失敗0・Overflow0の基準を変えない。
通過した場合だけ同じ人工27例/54条件（読解54+判定54=108 Call）へ進む。最大128 Call。
各言語90%以上/明確な非支持への誤支持0も維持する。既知少数の成功で主Development/Calibrationを代用しない。
初期3候補12 Call+固定文16 Call=実28 Callで、この候補を最大まで行っても累計156 Callの範囲。
概算10〜30分、VRAMは既存8B資源実測を基準とするが、読解後の入力/出力・実費は改めて測る。

通過後は他の旧既知誤り/正例を事前登録して回帰し、未知QAの主Developmentで読解誤りや過度な棄却も検証する。
これでも採用基準を満たせない場合は、取得済み範囲だけでなく別Model/Runtimeの資源・制約や研究上の選択肢を整理し、
統計/Validatorなど依存しない作業も続ける。意味未達のままGate 11やPhase 12へ進まない。
