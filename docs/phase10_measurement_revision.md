## 文単位の評価対象

### 現行処理の流れと、今回の修正が働く位置

1. 保存済みの質問・初回回答・実使用根拠10件を読み、Hashを照合する。初回回答を生成し直さない。
2. 初回回答の本文を一度だけ文単位に分け、本文が欠けずに再構成できることを検査する。
   例えば「署名は11時。発効も11時。」なら両方を残す。正しい文だけを抽出して採点を高くしない。
3. その固定文リストを使い、評価器へ渡す根拠の配列だけを元順序・逆順・Shuffleへ変更する。
   文リスト・質問・根拠本文は同じで、採点の前後に回答を書き換えない。同じ元順序の反復を対照にする。
4. 評価器は各文について「明示的な矛盾」「全詳細の支持」を返す。プログラムは固定RuleでLabelとFを計算する。
   実際には署名5時・発効11時なら、「署名11時」は矛盾である。日付が一致するだけで文全体を支持しない。
   ただし、この指示を入れてもModelの意味判定の誤りは残り得る。
5. 別枝で、元の質問・初回回答・元順序の根拠から一回だけ書換え候補を作る。
   同じ1回の生成内で根拠と初回回答の問題を点検し、最終回答を返す。並替えた根拠や評価器の結果は渡さない。
6. 初回回答と書換え候補を匿名化し、外部AIが実使用根拠・Reference/Goldで品質を採点する。
   内部F・判断・初回/書換えの区別を採点前に開示しない。全候補の品質Labelを固定してから対応を開く。
7. Fが0.7以上の経路は初回回答、それ未満は同じ書換え候補を選ぶとして、品質と費用を照合する。
   単独拒否はF=nullの別Fallbackで初回を保持する。F=1や「順序によらず正しかった」に数えない。

予備実験では、採用された場合にも書換え候補を収集しておく。
これは「書き換えれば改善したのに採用してしまった」という機会損失を後から測るためであり、
実運用の採用経路が書換え費用まで支払うという意味ではない。収集費用と経路ごとの費用を分けて記録する。

抽出Promptだけを強化した試作v2でも、空港名の由来が抜けた。
v3で、初回回答の本文を文単位で保持する決定的な抽出へ変更し、現在のv14でも維持する。
数値形式の引用マーカーと空白を除いて本文を再構成できることを検証する。
元回答以外を読まず、モデルによる言換え・取捨選択・事実訂正をしない。
単独の定型的拒否は別状態とし、拒否と事実を混ぜた回答は本文を残す。
未知の拒否表現は勝手に除外しない。引用と略語の判別・文分割には規則の限界がある。

これは**原子的な事実分解ではなく、複合した主張を含む文の支持判定**である。
全詳細が支持されて初めてsupportedとし、一部の明示的矛盾はcontradicted、支持不足はnot_supported。
Fはsupported文単位数/固定文単位総数となる。長い文と短い文の重みは同じで、
主張の細かさによる影響は限界とする。LLM抽出の抜けを順序効果に混ぜないことを優先する。
文の指示対象は固定の元回答・根拠の前後関係も参照する。

## 開発履歴: v2〜v7の意味判定・書換え・予算

- v2は意味上の比較を指示するPromptを試す開発診断。失敗も残す。
- v3は短い理由・証拠を生成した後にLabelを選ぶ。同じDecoder順序・引用候補集合を全根拠順序へ適用する。
- 3Bでは意味誤りが残るため、v4は評価・書換えに公式Qwen2.5-7B-Instruct GGUF Q4_K_Mを候補として使う。
  初回生成は既存3Bのまま。モデル規模だけで改善を主張せず、同じ診断を通す。
  [公式固定Revision](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct-GGUF/tree/bb5d59e06d9551d752d08b292a50eb208b07ab1f)の
  2ファイルを公式SHA-256で検証し、専用Manifestへ保存する。Runtimeは既存b11433のWindows CPU。
  以後の「自己評価」はRAG内部の評価機構を指し、初回生成と同一のModelによる自己採点という条件には限定しない。
  複数の変更をまとめた測定系改訂であり、Modelだけの効果を分離したAblationではない。
- 7Bのv4でも情報不足の誤支持が残った。同じボートの例を簡単な非制約形式では正しく判定したため、
  v6は大量の原文候補を列挙するDecoderをやめ、短いJSON構造・原文引用の事後照合へ変更する。
  1例だけでDecoderが誤りの原因だったと断定せず、新しい形式で全診断を再確認する。
  根拠を先、固定Claimを後へ置き、理由400文字→Label→証拠の順で出力する。
  引用は原文の直接一致、または大文字小文字を保持した単語・数値の連続列の一意一致に限って位置を解決する。
  語の追加/削除/並換え、否定や数値の変更、曖昧な複数位置への一致は失敗とする。
  Raw引用と解決後の原文・位置・方法を両方保存する。句読点・空白の差を許す位置解決であり、意味一致の保証ではない。
  この照合はLabelやFを修正しない。v6のJudge出力予約は4,096とし、本文は変えない。
- v7はv6のJudgeを維持し、書換えを同じ1回のCompletion内のJSON点検へ変更する。
  `source_facts`→`draft_issues`→`answer`の順で、根拠を先に確認し下書きへ引きずられる問題を検証する。
  Completion全体の予約は1,024、採用可能な最終回答はTokenizerで512以下と確認する。超過しても切詰めない。
  点検欄を最終候補や品質採点へ渡さず、追加の回答候補を選別しない。全出力Tokenを費用へ計上する。
  初回回答のままの誤った時刻、不要な拒否、禁止の取り違えを自然例と人工例で確認する。
- v3/v4の引用は原文の320文字以内、理由120文字以内、各文の引用最大2件。
  長い文書は同じ原文の短い連続部分も引用候補にする。全文書は入力に残す。
- v3/v4の補助Contextは12,288、Judgeの出力予約3,072、書換え512。入力＋予約を毎回検査し、超過時は失敗として保存。
  初回Baselineの4,096/512は変更しない。予約枠の増加は入力切詰めの許可ではない。
- 書換えは初回回答を未検証の下書きとして扱い、根拠から必要情報を確かめて誤り・不必要な拒否を修正する。
  元順序・同じ根拠・1候補共用・再検索なし・JudgeのScore/Feedback/Reference/Goldなしを維持する。

### 長い自然文脈での追加確認

7Bのv7は明確な人工15例と人工書換え3例を満たしたが、自然例では調印時刻の誤支持、
回答の言換えを原文引用として生成する形式エラー、書換えで誤った時刻を保持する問題が残った。
人工例だけの通過を測定系全体の完成とはしない。

v8以降は、初回生成3Bを維持したまま、内部Judgeと書換えに公式Qwen3-4B Q4_K_Mを候補として追加した。
[固定Revision](https://huggingface.co/Qwen/Qwen3-4B-GGUF/tree/bc640142c66e1fdd12af0bd68f40445458f3869b)と
GGUFのSHA-256を専用Manifestに保存する。Qwen2.5-7Bより大きいModelという位置付けではない。
初回生成と内部評価・書換えが別モデルである実験条件を記録する。

- v9以降のContextは16,384、Judge/書換えCompletion上限は各2,048 Token。
  Runtimeの推論予算を512 Tokenに固定し、実出力のToken列で終了タグと予算を監査する。
  最終JSONを含む全出力を費用に含め、最終回答は補助ModelのTokenizerで512以下と検査する。
  旧GeneratorとTokenizerが異なり、同じ文字量を保証する予算ではない。
- 補助生成はtemperature 0.6 / top-k 20 / top-p 0.95 / min-p 0 / presence penalty 0 / seed 42。
  これは初回Baselineのtemperature 0を変えない独立設定であり、全順序・同順序反復に共通である。
  公式のthinking推奨値を参考にしたが、presence penaltyを含め全推奨値と同一とは主張しない。
- Judgeは根拠・質問・固定文単位を受け取り、回答全文の重複入力を省く。
  Reference/Goldは渡さない。入力文単位には全文を残し、本文・IDの削除や切詰めはしない。
- 引用生成をやめ、実在するPassage IDを最大2件返す。
  監査用の原文はプログラムが対応する全文書を添付する。
  これはモデルが選んだ短い証拠Spanではなく、引用IDの存在も意味判定の正しさを保証しない。
- v10以降は「明示的な矛盾があるか」「全詳細が支持されるか」の二つを返す。
  true/false→contradicted、false/true→supported、false/false→not_supported、true/true→形式エラー。
  プログラムは意味判定を訂正しない。v11は三種類を示す架空の均衡したJSON例を追加する。
- 書換えは同じ1回のCompletion内で推論・根拠点検・問題点・最終回答を生成する。
  推論と点検欄は保存するが、外部品質採点へ渡さない。
  生成された推論文を、Model内部の忠実な思考過程の記録とみなさない。

v8/v9/v10は既知の時刻誤りを先行検査し、不通過のため残りを実行しなかった。
v9はFが1/3になったが、一つの誤支持と別の誤棄却が併存し、正しい修復判断だけで合格とはしない。
v11は誤った調印時刻を含む二文をcontradictedと判断した。一方、日付についての正しいtrue結論を
not_supportedとする誤りは残った。この自然例の全Label一致や一般精度100%を達成したとは記録しない。
この段階ではv11の残る診断と書換えを確認中で、新規10問の内部F・品質Yは未開示だった。

v11の自然書換えでは、誤った調印11時を5時へ訂正し、最終回答88 Tokenで保存できた。
ただし人工`time-absent`で意味説明は正しくても最終JSONの括弧を誤った。
完了済み出力を保持して開発候補を停止し、停止時の未完了呼出しは結果不明として残した。
この候補を採用して新規10問を評価することはしなかった。

v12/v13は推論終了タグ後だけ小さいJSON SchemaをDecoderに適用する。
固定Claim ID列・理由最大160文字・引用ID最大2件を制約し、Schemaは根拠の提示順に依存させない。
大量の原文引用Enumは復活させず、推論自体はJSON形式に拘束しない。
