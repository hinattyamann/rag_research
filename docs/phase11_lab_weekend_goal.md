## 2. Goal欄へ設定する本文

```text

計画や単体Testだけで完了にしないでください。Gate11の全実証拠・主/Cal証明・最終Validator成功と最終Manifest/Hashを確認し、研究日誌と仕様へ到達点を記録してCommit/通常Push/Remote一致を確認した時だけGoal完了です。人の操作が不可避の権限・接続・物理障害や未使用検証資料の枯渇では、証拠と必要操作を明記し、依存しない作業も尽くしてください。製品の利用上限や上位の状態管理規則は回避せず、未達を完了扱いにしないでください。通常の候補不合格・修正可能な障害・数時間の経過だけで説明を返して待機終了しないでください。
```

## 4. 継続ループ：障害時は実験を止め、原因を直して研究を続ける

1. ログ・入力・出力・Token・終了理由・資源・失敗/未知を保存する。応答不明を非支持0、費用0、成功へ変えない。
2. 意味不適合とRuntime/通信/JSON/入力超過/実装不具合を区別する。正しいLabelでも理由や引用が誤っていれば診断へ残す。
3. 次の仮説と変更を記録する。まず生成0・最小の関連Smokeで切り分け、局所的な修正ごとに全70/84 Callを機械的に反復しない。
4. プロジェクト内の修正・隔離Runtimeビルド・自身が起動した終了/異常LLMプロセスの後始末と新プロセス起動は、この依頼の範囲で行う。たとえば固定llama.cpp SourceのCUDA Graph OFFは、原因確定ではなく別条件の検証候補として扱う。
5. 推論に影響する変更は別候補/Runtime/Config/Runへ分ける。Model/Runtime/Prompt/Sampler/Schema/Coreの一致を検証し、変わった範囲の形式・意味・回帰証拠を取得する。不変の証拠は根拠を付けて再利用する。
6. 不合格候補を保存し、Development内で次の候補を改善する。検査例の固有名・ID・正解ラベルをPromptへ埋め込まない。小さな既知集合への過適合を記録し、未使用データでの確認を残す。
7. `automatic_retries=0`の旧Runはそのまま残す。回復用の新実行を認める場合は、原因に対応する変更、対象、未知の扱い、有限の試行計画を事前登録する。同じ入力/条件を成功が出るまで再抽選したり、失敗QAだけを置換したりしない。
8. 確定済みの純粋なソフトウェア不具合で、要求未送信をJournalから証明できる場合のみ、既存成功を保全した未送信分の継続を検証する。不明な送信結果を未送信扱いにしない。

Driver更新、OS/セキュリティ設定変更、GPU Reset、マシン再起動、他人のプロセス終了はこの依頼の自動実施範囲に含めない。
そうした操作が唯一の解決策なら、理由・影響・必要操作を残し、可能な別Runtime/実装/解析/文書作業を先に完了する。
Sandboxや自動承認レビュー、アカウント利用上限を回避する仕組みは作らない。

## 5. 予算・監視・中断復帰

- 各Run開始前に対象数、全文の文数、順序/反復数から有限な必要Call・Token・時間見積り・個別timeout・資源監視を登録する。全体に固定の4時間等の打切りを再設定しない。台帳は新チャットや候補の切替えでも累積する。
- 旧の188/14400秒/候補1個Guardを素通りしない。本書による新許可を記録した別VersionのProtocol/実行入口/台帳と回帰Testを作り、Known→Main→Cal→FreezeのVersion/Hashを整合させてから使う。
- Main/Calの旧1660 Call/言語も、純粋な実行資源枠として不足する場合は、結果の良し悪しを見る前に、選定済みQAの全文・全試行に必要な量を別Versionへ算定・登録できる。分母・選定ID・品質/意味基準・反復設計は変えず、失敗の再抽選のために増額しない。
- 長時間Nativeは固定Commitの専用Checkoutと実行台帳へ結び、既存Handle/Journal/Server Logを定期確認する。監視間隔や最後の更新時刻、現在の工程、次工程を日誌/進捗資料へ残す。
- 「実行中、待ちます」という説明だけでターンを終えず、実際に待機Handleを確認するか、意味のある独立作業を行う。自動継続を維持するためだけのダミー呼出しや、無益な高速ポーリングはしない。
- 個別5 QAの段階Sessionが終わっても、同じ固定Protocolで残る予定QAへ順次進む。段階Sessionの上限を、ユーザーの手動再生が必要なGoalの停止点にしない。
- 電源・ネット・スリープ・アプリ停止・サービスの利用上限は、プロンプトだけでは解消できない。自動継続や復帰を保証したと記録しない。再開時は台帳と実プロセスを照合し、実行の重複と未知要求の再送を防ぐ。

## 6. 採用・実験の順序と変更しない条件

### A. 評価器を採用するまで

支持Recall/非支持Specificityを**それぞれ0.90以上**とする`support-binary-v2`を維持する。
C↔NSの誤りは三分類診断へ残す。支持10文/非支持5文、正負各3 QA/文書Group以上という最低被覆と不足時不通過を維持する。
曖昧Expectedは精度からだけ除き、F/QA/費用の分母に残す。

全15 QA/42文/元逆30条件/84 Callの新鮮な回帰を完了・監査し、Healthと意味基準を両方満たした候補だけを次へ進める。
形式成功、Smoke成功、過去の8B/9Bの部分成功、87.5%の丸めだけでは採用しない。
変更した候補には必要な日英意味検証も行い、英文回帰だけで日本語を保証したことにしない。

### B. Main日英各20 QA

元の選定Manifestを使い、全経路、全文/固定文、最大9試行の順序変更対同一順序反復、一回書換えを実行する。
両言語の全回答品質と全Expectedを封印してから、内部F/採用判断/候補対応を開く。
各言語で全20 QAの処理、Health、二値の両90%、被覆、完全比較各10 QA以上、品質・費用・失敗と実主証明書を確認する。
不適合時は失敗を残してDevelopmentへ戻り、変更版の必要検証を行う。使用済みのMainを新しい未使用データとは呼ばない。

### C. 別予約Calibration日英各20 QA

採用する候補・Protocolを固定してから、元予約の別20 QAずつで同じ基準と全品質/Expected封印を確認する。
未完了/失敗QAの補充や、内部結果を見ての都合のよい選び直しはしない。
Calの結果を条件調整へ使ったら、その集合は使用済みとして保持する。
改訂候補の独立確認に別集合が必要になった場合は、Evaluationに触れず、元の許容Splitの未使用・非重複Groupから
各20 QAを結果を見る前に別Protocolで固定できる。旧Calの不通過、選定・調整・検証の全履歴と反復選択の限界を報告する。
合格する集合を探すための再抽出はしない。適格な未使用集合が確保できなければ、その事実を真の未達要件として記録する。

### D. 最終固定と終了

Main/Calの実測、比較可能数、Group単位CIと採点負担から、最終EvaluationのN/資源/統計を決める。
Dataset/Split/ID、Model/Runtime、Prompt/文単位、F閾値0.7、順序/反復・Seed、裸拒否一回書換え、品質/停止/欠測を固定する。
QA内で初回回答・根拠本文/ID/Titleを固定し、順序だけを操作する。Goldを推論へ渡さず、Evaluation本文/回答/結果で調整しない。
日英の別Dataset差を言語だけの因果とせず、効果が大きい・有意・品質改善したことを合格条件にしない。
実際の採点者、human_reviewed=false、厳密なModel識別子の取得可否と履歴隔離の実情を記録する。

最終Validatorを**実証拠で**通し、証明書/最終Manifest/Hashを照合してGate11全項目を確認する。
日誌・仕様・実装・条件を一致させ、適切な`uv run pytest`/`uv run ruff check .`と最終差分確認を行う。
意味ある単位で今回分だけCommit・通常Pushし、Remote先端一致を確認して完了報告する。
**Phase12の本実験は開始しない。** 未達・権限/物理障害・未使用集合の枯渇は、完了の代わりに具体的な証拠と必要操作を報告する。
