Source/Split/Baseline/Phase 8/9の旧設定・旧ソース・旧Manifestを上書きしていない。

## 2. 実行方法

```powershell
uv run --locked python scripts/run_pilot.py select
uv run --locked python scripts/run_pilot.py baseline
uv run --locked python scripts/run_pilot.py internal
```

出力Rootは`data/runs/pilot/phase10-twenty-v1/`。
Baselineは`baseline/`、内部実行は`internal/`、匿名採点資料は`quality/ready-001/`等へ分離する。
外部採点へ渡すのは匿名Packet/HTMLのみとし、privateと付く内部結果・対応表を採点前に開かない。
進捗の`progress.json`とConsoleは質問数等を表示し、内部Fや判断・回答本文を表示しない。
内部Manifestが固定済みのRunへ`baseline`を再実行する場合は、CLIがHashを検証して読取専用で再利用する。
BaselineのSessionを追記して参照Hashを変えず、追加Completionは0回となる。

採点は次のCLIで候補を一つずつ開き、理由・原文引用を含むDecision JSONを書いて保存する。
各候補の確認時間は実際に資料を開いてから保存するまでの経過時間であり、人手時間ではない。

```powershell
uv run --locked python scripts/assess_pilot.py open --packet 1
uv run --locked python scripts/assess_pilot.py save --packet 1 --decision "decision.json"
```

確認者表示名はリサーチャー01、実採点者はCodex AI、human_reviewed=falseとする。
完了済み候補への再採点で元Labelを上書きせず、訂正が必要なら別の改訂履歴を作る。
判定不能を0/1へ強制しない。元文書の引用IDと原文の完全一致を既存Validatorで確認する。

全対象の採点後に初めて対応表と内部結果を開き、次のCLIでPilot Reportを作る。
事前のHealth Gateが停止した場合は、実施済み範囲を採点し、未実施IDもReportに残す。

```powershell
uv run --locked python scripts/run_pilot.py report
```

## 3. 評価範囲と制約

採点側はReference/Goldを知るが、内部のF/条件/判断/段階を伏せる。支持の確認には実使用Contextを使う。
今回のPilotは同じ作業セッションで新しい内部結果を伏せて採点するため、完全な履歴分離とは主張しない。
Codexの正確なモデル識別子はこのセッションから取得できずnullとして保存する。
本番の専用セッション・モデル固定と妥当性検証はPhase 11で確定する必要がある。
今回の再確認を、人間との一致率や独立した複数評価者の一致として報告しない。

最初の2候補では「共同歌唱の情報不足」と「記載された参加歌手という事実」を区別するため、
内部結果の開示前に観点判定の訂正を記録した。総合Labelは変わらない。
`quality/assessments/packet-001/revision-history-001/`に元の採点と訂正履歴を保持する。
訂正の追加時間は個別計測していない。Reportの確認時間和は初回の記録済み時間であり、全採点作業時間ではない。
3〜20問では候補を開く前に質問だけから必要情報と曖昧さを整理し、`question_only_checklist.json`へ保存した。
これは凍結した3観点の変更ではなく、Reference/Goldによって質問の解釈を確認するための補助記録である。

主比較は両群の必要Trialがすべて有効で、ペアを作れる共通QA。
順序群と反復群の不一致率を質問内でまとめて差を取る。各ペアを独立QAとして水増ししない。
部分失敗・Claimなし・品質不明・書換え失敗・初回失敗・Health停止後の未実施を別に報告する。
費用は実験の収集と各条件の経路、外部AI採点の時間を分ける。経路のStep和を実測Latencyとは呼ばない。
本Pilotの記述集計は、本実験や正式な信頼区間の代わりにはしない。

## 6. 具体例と測定上の問題

### 6.1 グラナ: Fは揺れたが修復判断は変わらない

質問は`what does the grana do in a plant cell`。
初回回答と4つのClaimを固定し、光依存反応の根拠`865087067_496-958`の位置だけが変わる条件を比較した。

| 条件 | この根拠の位置 | F | Claim c3「光依存反応はチラコイドで起きる」 | 判断 |
|---|---:|---:|---|---|
| 元順序 | 9 | 1.00 | supported | 採用 |
| 逆順 | 2 | 0.75 | not_supported | 採用 |
| Shuffle 1 | 1 | 0.75 | not_supported | 採用 |
| Shuffle 2 | 10 | 1.00 | supported | 採用 |
| Shuffle 3 | 9 | 1.00 | supported | 採用 |

同一順序5回のFはすべて1.00。逆順とShuffle 1では、本文に光依存反応の明示があるのに
「文書に情報がない」と判定した。これはFの順序感度の具体例だが、全Fが固定閾値0.7以上なので修復判断へは伝わらなかった。
この1例から、根拠を後方へ置けば一般に良いとは結論しない。反転を作るため閾値を事後変更しない。
この例はスコア変化を見た後に選んだ探索的な説明例である。

### 6.2 休戦協定: 順序に安定していても正しいとは限らない

回答は「1918年11月11日午前11時に調印」と説明したが、実使用根拠は調印が午前5時、停戦発効が午前11時と区別する。
誤った時刻はClaim c1/c2へ抽出されている。それでも9試行すべてでsupported、F=1.00、採用となった。
Judgeは5時と11時の原文を正確に引用しながら、意味上の区別を誤っている。
JSONの整形式や引用の原文一致だけでは、評価器の意味判定の正しさを保証できない。
外部AI品質は初回・書換えともY=0で、書換えも時刻誤りを解消しなかった。

詳細監査例1（歌手）と4（休戦）は内部F開示前に選んだ診断例である。
無作為の精度標本ではなく、この例からJudge誤判定率は推定しない。

### 6.3 Claimなし8問を全て同じ原因にしない

- 5問は初回が情報不足の拒否文であり、対象世界についての実質的Claimがない。拒否の回答品質とは別に扱う。
- 残り3問（歌手、West Bengal、アルバム名）は事実を述べる本文があるのに空のClaim列を返した。
  これらを「順序によらず安定」と数えず、比較不能として残す。
- 抽出成功例にも、空港の命名対象Butch O'Hareや、ベルリンの壁の建設目的を落とす例があった。
  Fの分母になるClaimの網羅性を先に確認する必要がある。

王室財源の例のように、本文の事実は支持されても質問への説明が不足する回答もある。
Y=0とF=1の組合せだけで、Faithfulness Judgeの意味判定が誤りだったとは断定しない。

### 6.4 出力上限と採点資料

洗礼の質問では7 ClaimのShuffle 2が1536 Tokenの出力上限に達し、`Incomplete output: finish=limit`となった。
Fはnullのまま保持し、再抽選やF=0への変換をせず、QAを完全比較から除いた。

全20問でSelected EvidenceとGold本文の文字列対応を監査したところ、犬の質問で
Reference/Selected Sentenceの14,700年とGold本文の14,200年が一致しなかった。
資料を黙って修正せず、どちらかとの数値一致だけを品質判定に使わなかった。これはCorpus全体の誤り率を測ったものではない。

ローカルQwenの実呼出しは、初回20回、抽出20回、Judge108回、書換え20回、合計168回。

Judge1回の平均は108.12秒だった。Codex採点の記録済み初回確認時間和は1063.16秒（約17.72分）で、
訂正・全体監査の追加時間を含まない。人間の作業時間として利用しない。

運用方式を同じ保存済み候補から再構成すると以下になる。

| 方式（20問合計） | ローカル呼出し数 | Step時間和 | 最終品質 reliable / unreliable / 不明 |
|---|---:|---:|---|
| 修復なし | 20 | 1052.81秒 | 11 / 7 / 2 |
| 常時1回書換え | 40 | 2167.01秒 | 12 / 7 / 1 |
| 元順序の判断で書換え | 54 | 2706.52秒 | 11 / 7 / 2 |

判断方式は書換えを2回に抑えるが、抽出20回とJudge12回の負担があるため、呼出し数やStep時間和では常時書換えを下回らない。
これは検索・起動・外部採点を除くStep和であり、実測の一連の応答Latencyではない。
今回の欠測率を含む時間を、そのまま修正後の100〜200問へ比例拡大して規模確定はしない。
