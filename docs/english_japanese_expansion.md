# 英語・日本語データによる根拠提示順序感度の比較方針

決定日: 2026年10月21日。ユーザーとの研究相談で採用した拡張方針を記録する。
研究目的は[研究計画](rag_research_plan.md)、実装仕様は[実装計画](rag_implementation_plan.md)、
工程・現在地・Gateの正本は[ロードマップ](research_roadmap.md)とする。

## 1. 決定した範囲と未実施事項

英語CLAPNQに、別途作成された日本語データセットを加え、根拠の提示順序に対する
RAG内部評価の感度と、採用/一回書換えの判断・最終回答品質・費用への影響を比較する。
翻訳した同一問題の日英対応データを主実験には使わない。
日本語データはCLAPNQとできるだけ課題・回答・根拠の構成が似たものを選ぶ。

目的は、英語での現象が日本語データでも再現するか、観測する差がどの条件と関係するかを調べること。
日本語の方が不安定になることや、有意な差が出ることを前提にしない。
提示順序による判断変化と、意味上の誤判定を区別し、安定して誤る評価器も監査する。

方針決定時点では文書化のみだった。同日のGoal実行で[候補比較・Source選定](japanese_dataset_selection.md)と
固定版原QAの取得・構造監査を実施した。選定したのは`baobab-trees/wikipedia-human-retrieval-ja`。
本文Corpusは取得中。日本語文単位のComponentは実装・Test済みだが、分割・全Pipeline実走・
予備検証・条件凍結・本実験は未完了。JQaRAやJaQuADを採用したわけではない。
既存の英語Phase 1〜10の完了記録とCPU/GPU Runは保持し、日本語対応の完了へ読み替えない。

## 2. 比較から主張できる範囲

英語と日本語で別データセットを使うため、言語とデータセットの違いは完全には分離できない。
差があっても、日本語そのものが原因、語順の性質が原因、または全てのモデルで同じと断定しない。
結果は、採用したモデル・処理系と英語/日本語データの条件における比較として報告する。
選定時に仕様を近づけ、回答長・文単位数・根拠数・検索品質等を記録して解釈を補う。

各QA内では質問・初回回答・実使用根拠・固定主張を保存し、評価器へ見せる根拠順序だけを変える。
同じ順序の反復を対照にし、生成器の順序感度や再検索の影響を混ぜない。
日英のQA同士に対応関係があるとは仮定しない。

## 3. 日本語データセットの選定基準

CLAPNQの仕様は[Dataset Guide](clapnq_dataset_guide.md)を基準に、候補の一次資料と実例を比較する。
件数の多さだけで決めず、以下の比較表、残る差、採用/不採用理由をPhase 11で保存する。

| 観点 | 優先する性質・確認事項 |
|---|---|
| 言語・課題 | 翻訳対ではない日本語QA。テキストを根拠とする、一般的な知識質問への回答 |
| 回答形式 | 固有名詞等の短い抜出しだけでなく、説明・複数の事実を含む自然な長文回答を持つ |
| 根拠 | Referenceと根拠本文・文書IDの対応を確認できる。可能なら文単位の根拠もある |
| 文書領域 | Wikipedia等、CLAPNQに近い百科事典領域を優先する |
| 検索 | 再現可能な検索Corpusがある、または同等の検索条件を構築できる。候補集合のみの場合は制約を明記する |
| 非テキスト要因 | 図表読解・画像・OCR品質が必須となる課題は優先しない |
| 分割・規模 | 記事/文書単位で開発・Calibration・未使用Evaluationを分け、各用途の有効QA数を確保できる |
| 来歴 | 公開元・Revision・License・取得条件・Hash、質問/回答/根拠の作成・確認方法を保存できる |

回答長・必要な事実数・根拠の分散、回答可能性、参照回答の品質、質問の作り方も比較する。
完全に一致する候補がなければ、相違点と必要な追加Annotation/Corpus構築の負担を記録する。
Gold文書だけを追加した条件や、短答を独自に長文化した条件を、通常検索のCLAPNQと同等と扱わない。
仕様を近づけるために翻訳データへ切り替えたり、大幅な課題変更を採用済みとして扱ったりしない。
方針の再検討が必要になった場合は、その理由と研究範囲への影響を明示する。

## 4. Phase 11で準備・検証すること

1. 上記の候補比較から日本語Sourceを決め、Source/Corpus/Reference/根拠の来歴を保存する。
   記事/文書GroupによるSplit、重複・欠損の扱い、ID/Seedを決め、調整用と本実験用を分離する。
2. 既存QA/根拠形式へのAdapterを用意し、Datasetと言語をRun/Manifestに記録する。
   CLAPNQのPath/ID/Titleや選定処理への依存を点検し、旧データ・Manifest・Runは上書きしない。
3. 日本語の検索用分割とEmbedding、初回生成・Judge・書換えの指示文と言語方針を確認する。
   モデルは可能な限り日英共通とし、変更が必要なら比較条件への影響を明記する。
4. 「。」「！」「？」等の文境界、引用、拒否文、主張なし、本文保持と支持/矛盾の意味判定を検証する。
   Fの分母となる文単位の定義をそろえ、日本語だけ段落全体を一単位とする実装上の差を避ける。
5. 実Tokenizerで入力/出力予算を確認し、QA内の全順序で同じ本文を保持する。
   日英の実Token長・根拠数・文単位数の差を記録する。同じ上限でも情報量が等しいとは仮定しない。
6. 日本語の少数Development例で、検索から匿名品質採点・集計まで予備検証する。
   20〜30問は出発目安で、言語差を結論する件数や本実験件数ではない。
   意味妥当性・比較可能数・失敗/拒否・時間・採点負担を確認し、反転率の大きさを合否にしない。
7. 共通処理を変えた場合は英語側でも回帰確認する。既知例で修正した後、別の未使用Calibrationで
   両言語の候補条件を確認する。使用済みQAを未使用へ戻さず、新規結果を見る前に停止条件を保存する。
8. 両言語の本実験対象・件数・設定・分析計画を固定し、凍結Manifestと確認根拠を保存する。

英語側の既知の誤支持と拒否Fallbackの検討もPhase 11の残作業として継続する。
日本語の追加だけでは既存Judgeの妥当性の問題は解消しない。
Python実装変更時には、変更した境界のTestと`uv run pytest`、`uv run ruff check .`を実施する。

## 5. 本実験前に固定する比較・統計

- 順序条件・同一順序反復数・Seed方針・呼出し順・有効性Ruleは可能な限り日英で共通にする。
  Model/量子化/Runtime、指示文の言語、文単位、閾値、予算、拒否/失敗Fallback、外部AI採点基準も保存する。
  言語別に異なる設定が必要なら差と理由を記録し、単純な言語差へ帰属しない。
- 各QAで「順序変更群の判断不一致率 − 同一順序反復群の判断不一致率」を求め、言語別に平均する。
  日英比較ではこの平均の差（日本語 − 英語）と95%信頼区間を主な比較に加える。
  各Dataset内のQA/文書Groupの依存を保って再標本化し、日英の独立なQAを対応標本にはしない。
  具体的な再標本化・検定・多重比較の扱いはPhase 11で固定する。
- 一方の言語だけで有意となったことを言語間の差の証拠にしない。全Trialや全判断ペアを独立QA数に数えない。
- 言語別の反転例率、独立AI品質による四遷移・悪化・改善見逃し、費用も比較する。
  有効比較QAと全選定QA、失敗・拒否・不明の分母を言語別に示し、都合のよい補充や除外をしない。
- 根拠数・入力長・回答長・文単位数・検索品質等を記述する。条件別比較や調整を行う場合は
  少数の項目・方法を事前に固定し、残るDatasetの違いを明示する。
- 現行の英語Evaluation Answerable候補は564問、英語200問は未凍結の案である。
  この200問を日英合計または各言語の採用件数と読み替えない。言語別の有効数・推定精度・費用から決める。
  日本語の追加は英語の有効標本数を増やすこととは区別する。

### 実機と初期資源見積り

開始前Fetch成功、`main / 1f3fb57`と`origin/main`の差0/0、未Commit変更0。
実行中のPython/uv/pytest/llama-serverは確認されなかった。
実機はRTX5060Ti・VRAM8151MiB（確認時空き6819MiB）、RAM7.5GiB（利用可能約3.0GiB）、
Disk空き385GiB。既存のRaw/Processed/Index/Model/Runtime/Runは約7.5GiB。
モデルは同時常駐を避け、検索・索引作成はStreaming/メモリ制約を前提にする。

- Aは一次資料と小さい開発用Sampleの確認で進め、LLM生成0回。
- B/Cの容量はSource選定後、公開ファイルのサイズと文書件数から再見積りする。
  既存英語Corpus178,890 PassageのIndex約471MiBは参考値で、日本語の容量保証には使わない。
  384次元float32のVector本体は100万Passageあたり約1.43GiB。本文・索引・Modelは別途必要。
- Dを日本語20問で全問比較可能として計画すると、最大Judge180回と書換え20回に初回20回が加わる。
  既存GPU20問の補助128 Task/957.37秒を単純に延ばすと補助200 Taskは約25分だが、
  日本語入力長・モデル/指示文変更・起動・採点を含まない参考値。実測後に更新する。
- Eも各言語20問なら補助は最大400 Task、同じ単純換算で約50分。
  件数・採用基準・実行上限はDの後に新規結果を見ず保存し、ここで確定済みとは扱わない。
- GPU実験はコード・設定をCommit固定したCheckout/Worktree等で行い、旧Runを再開・上書きしない。
