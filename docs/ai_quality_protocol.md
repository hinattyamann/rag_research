## 1. 役割と情報の分離

初回20問の内部Judgeは固定Qwen2.5-3B/llama.cppによるFと採用/一回書換えの判断を行う。
測定系改訂後の少数再確認のModel/予算は第5節に別記する。外部採点の基準は共通である。
外部品質採点はCodex AIが質問・候補・元順序の実使用Context・Reference/Goldを読み、下記のYを付ける。
Reference/Goldを内部Judge、初回生成、書換えへ渡さない。
品質採点には条件名、内部F、採用判断、候補段階、内部JudgeのClaim/理由を渡さない。
候補は匿名化し、質問ごとの同一候補は一度だけ採点する。候補本文から段階を推測できる可能性は残る。
内部実行の進捗出力に評価値を載せず、採点前に内部結果を閲覧しない。

Pilotは既知の5問とそのTitleを除外したDevelopment Answerable 20問、異なるTitleを一つずつ選ぶ。
選定はSeed42とIDのSHA256昇順で、結果を見る前にManifestへ固定する。失敗例を別質問で補充しない。
20問は以前のCPU実測と品質監査の負担を踏まえ、計画の20〜30問の範囲の下限に固定した。
内部Prompt/閾値0.7/9条件/原文保持/書換え1回/再試行0はPhase 8 v5・Phase 9から維持する。
内部試行前にHealth Gateを定める。先頭5問で完全に採点可能なQAが3問未満、または実Judge Taskの
形式/Runtime失敗率が25%を超えた場合、残りへの内部試行を止めて測定系の改訂を検討する。
入力超過は1問でも確認した時点で停止する。停止済み/未実施を残し、質問を補充しない。
この停止条件はFの値・判断反転・品質改善の大きさからは決めず、初回の内部評価前に固定する。

## 2. 採点手順と定義

1. 質問の要求と必要な答えの要点を記録する。
2. 回答全体の主張・欠落・引用を確認する。
3. 実使用Contextの全Passageと各主張の対応を確認する。
4. Referenceの代替回答、Goldの原文を確認する。Referenceとの表現一致やGold取得を合格条件にしない。
5. essential_answer、no_major_error、context_supportをpass/fail/uncertainで記録する。
6. 要点、理由、原文に一致する証拠、確認者表示名、AI実行者、時間・日時・来歴を保存する。

- reliable / Y=1: 3観点すべてpassで、実使用Contextに支持される根拠を保存できる。
- unreliable / Y=0: 1観点以上の明確なfail。その他がuncertainでも確定できる。
- indeterminate / Y=null: 明確なfailはなく、質問の曖昧さや支持の不確実性が残る。
- pending: 未実施。判定不能に変換しない。

引用だけの回答は必須要点fail。事実命題なしの観点は現行Schemaでuncertainとし、適用対象外と理由へ明記する。
支持されない主張と、外部世界で偽の主張を区別する。Goldだけで実使用Contextの支持を補わない。
Yが不明な候補の品質遷移は未知とし、改善/悪化/見逃しを確定しない。

## 3. 来歴と妥当性

AI採点であることをJSONの理由と別来歴に明記し、human_reviewed=falseを保持する。
表示名はリサーチャー01とし、実採点者はCodex AIと区別する。時間は人手作業時間にしない。
候補Hash、Packet Hash、完全一致引用、全候補ID、3観点とLabelの整合を既存Validatorで確認する。
AI判定と内部Fの一致を品質の正解としない。JSON検証は意味上の正しさの証明ではない。
明確な正誤/不足を持つ検証例、抜取再確認、不確実な例の監査をPilotで行う。
再確認の一致は正しさの証明や独立した複数評価者の一致と呼ばない。

本番では採点専用の独立入力/セッションと、モデル識別子・Prompt・原入力・出力・実行条件の保存を準備する。
モデルを固定できなければその制約を明示し、Phase 11で再現性の範囲を確定する。
Pilotの同一作業セッションで採点する場合は、過去の開発例・研究目的の知識があると記録し、
新しい20問の内部評価値を伏せても、完全な履歴分離を達成したと主張しない。

## 4. Gateと後続工程

Phase 9の開発ゲートはAI代行で二候補・判断・品質・費用の対応を確認する形へ変更する。
既存3候補で引用のみY0、文章候補は不明、Pradaは同文Y0であることと各経路の対応を照合済み。
この範囲でPhase 9のソフトウェア確認を完了とし、独立した人手確認を次工程の前提にはしない。
AI採点そのものの妥当性と本番の固定方法はPhase 10〜11で検証する。
Phase 10は20問の内部試行・書換え・AI採点・欠測・費用をまとめ、継続/改訂/本番規模を判断する。
順序反転や品質改善を発見することをGate条件にはしない。最終Evaluationで条件を調整しない。

## 5. Phase 10修正後の少数再確認

初回20問は履歴として保持する。[測定系修正記録](phase10_measurement_revision.md)の再確認では、
旧20問と既知Titleを除いたDevelopment Answerable 5問を、推論前に別Manifestへ固定する。
文単位の固定主張、意味比較を先に書くJudge、短い引用、補助Context 12,288/Judge出力予約3,072を候補とする。
3Bの意味判定が診断に通らない場合は、初回3Bを維持してJudge/書換え側の7B候補を別Runで検証する。
判断閾値0.7、元順序の共用初回を含む9試行、元順序による共通書換え1回、再試行0は維持する。
5問中3問以上の完全比較、Judge失敗0、入力超過0を実行面の目安とし、
事実回答の網羅性と意味判定は別途監査する。反転・品質改善は完了条件ではない。
外部AI採点の3観点・匿名化・全候補固定後の開示・来歴保存は本Protocolのままとする。
既知の診断例は開発用の回帰確認であり、内部結果を伏せた新規候補採点と区別する。

初回5問の拒否3問を機械的な本文有無だけで確認したため、内部F/Yの開示前に追加5問を固定した。
全10問を残し、CohortごとのHealth Gate不通過も隠さない。追加計画と完了基準は
[測定系修正記録](phase10_measurement_revision.md)と専用Manifestによる。
再確認用の検証候補は`configs/order_phase10_v14.yaml`。初回生成は旧3Bのまま、内部Judgeと書換えは
専用Manifestで検証したQwen3-4B Q4_K_M / llama.cpp b11433 Windows CPUを使う。
補助Context8,192、Judge/書換えCompletion予約各2,048、Runtime推論予算512、
temperature0.6 / top-k20 / top-p0.95 / min-p0 / presence penalty0 / seed42とする。
Judgeは矛盾有無/全詳細支持を返し、固定Ruleで三Labelに対応付ける。原文全文は引用IDからプログラムで添付し、
モデルが選んだ短い証拠Spanとは扱わない。形式検証と意味上の正解を区別する。
v11の最終JSON括弧誤りを受け、推論終了タグ後だけ小さいJSON SchemaをDecoderへ適用する。
SchemaのClaim列・引用ID集合は固定し、根拠の提示順で変えない。Labelの意味誤りを事後訂正しない。
書換えは1回のCompletion内に推論・根拠点検・問題点・最終回答を生成し、最終回答を補助ModelのTokenizerで
512 Token以下と検査する。初回GeneratorとはTokenizerが異なる。全出力を費用に含める。
品質採点には推論・点検欄を渡さず、通常どおり最終候補の本文だけを同じ3観点で採点する。
二つのCohortの全候補を採点・固定するまで、どちらの新規内部F/判断/候補段階Mappingも開示しない。
開発診断・候補採用条件と残る意味誤判定は修正記録へ残す。これをPhase 11の最終条件凍結とは呼ばない。
