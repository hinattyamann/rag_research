## 朝の最初の操作

### 1 研究室PCの現在の会話へ停止プロンプトを貼る

研究室PCで評価器改善を行っていた会話を開き、[研究室PC用プロンプト](phase11_v23_fixed_experiment_handover_2026-10-28.md)の「1」のコードブロック内を貼る。
本文そのものをノートPCやGitHubからコピーするので、この操作に研究室PCでのPullは不要。「ファイルを読んで」とパスだけ伝える方法は、未取得のファイルには使えない。

Codexが新規投入を止め、実プロセスを確認し、Raw/Journal/費用と変更を保存して、確認済みの変更をCommitする。ノート側の更新を先に取得する必要があるため、この段階ではPushを必須にしない。
旧Goalがpausedで、所有する実験プロセスも終了・保全済みであるという報告を確認する。画面が止まっているだけでは実処理の終了確認にならない。

### 2 新しい会話で同期と準備Goalを始める

同じリポジトリを開いた研究室PCの新しい会話へ、[研究室PC用プロンプト](phase11_v23_fixed_experiment_handover_2026-10-28.md)の最新「2」のコードブロック内を貼る。まだ手元にない場合はノートPCやGitHubから本文をコピーする。

「2」の冒頭でCodexがGit状態と追跡先を確認し、Fetchする。研究室側の保全Commitとノート側のCommitを確認・必要に応じ統合し、検証後に通常Pushする。双方に独自Commitがあれば、ff-only Pullだけでは統合できない。未Commit変更の破棄やforce pushで解決しない。

同期後、Codexが最新版のプロンプトと本書を読み、v23の再現・単独実行用プログラム・動作確認を進める。この間はCodexを使う。長時間の実QA収集はユーザーが起動するため、準備Goalが勝手にMain/Calを完走することは求めない。

### 3 操作を引き渡す報告を受け取る

準備完了時、Codexから次の内容を受け取る。ここで準備Goalは完了する。生成0と合成テストの成功を、実QAやGPU長時間運転の成功とは扱わない。

- 実際の作業ディレクトリ、固定Commit、Protocol、Run保存先。
- 通常の端末でコピーして使う、先頭1 QAの起動・続行・状態確認・停止・再開の実コマンド。
- Codexを閉じても続くことの確認方法と、端末を閉じてよい手順。tmux等を使う場合は、切離しと戻り方も含む。
- 読むべき公開状態ファイル、採点待ち・失敗時にコピーする報告文ファイル。
- 次の担当が「ユーザー」か「Codex」か、および次に行う操作を一つ。

コマンド中のRunや設定が架空の例・未入力のプレースホルダーのままなら、準備完了にせず、実在するものを使ったコマンドへ確定してもらう。

## Codexを使う区切りと使わない区切り

| 表示する状態 | 次の担当 | ユーザーの操作 |
| --- | --- | --- |
| 準備中 | Codex | 準備・検証・コマンドの引渡しを待つ |
| 起動準備完了 | ユーザー | 通常の端末で提示された起動コマンドを実行 |
| 収集中 | プログラム | CodexのGoalは継続させない。状態確認コマンドだけで進捗を確認 |
| 先頭1 QA確認完了 | ユーザー | 問題なく完了していることを状態表示で確認し、提示された同一Runの続行コマンドを実行 |
| Main収集完了・採点待ち | Codex | 下のMain報告文を新しい会話へ貼る |
| Cal起動準備完了 | ユーザー | 提示されたCal起動コマンドを通常の端末で実行 |
| Cal収集完了・採点待ち | Codex | 下のCal報告文を新しい会話へ貼る |
| 失敗・停止・結果不明 | Codex | 再起動せず、下の停止報告文を貼る |
| 採点・解析完了 | ユーザー | 図表・原稿・限界と次の操作を確認する |

この振分けは、Codex側の引渡し表示とプログラム側の状態遷移で案内できる設計とする。ユーザーが実験内容から毎回判断する必要を減らす。
ただし、Codexを自動起動したり、勝手に会話へ結果を送ったりする仕組みではない。「Codexへ報告」と表示されたら、ユーザーがCodexを開いて報告文を貼る。収集中は研究室PCを稼働させ、実行中のCheckoutへPullしない。

## Mainを起動して待つ

1. Codexから受け取った作業ディレクトリへ移動し、先頭1 QA用の実コマンドを通常の端末で実行する。
2. 公開状態表示で正常な先頭1 QA確認完了を確認する。Fや判断結果を開く必要はない。
3. 同じRunの続行コマンドを実行する。成功した先頭1 QAを再生成しない。以降は事前登録済みの段階をプログラムが順に進める。
4. 独立動作を確認した手順で端末を切り離し、必要ならCodexを閉じる。朝夕などに公開状態を確認し、異常を見つけたら保存された停止理由を報告する。
5. Mainの日英全予定対象の収集が揃った時だけ「Main収集完了・採点待ち」とする。5 QA単位の正常な区切りや先頭1 QA完了、単なるexit 0を全Main完了と取り違えない。

Mainは日英各20 QA。最初の1 QAや途中5 QAはこの40 QAに含まれ、別の追加実験ではない。
「収集完了」は採点・研究上の基準通過・論文完成とは別の状態である。

## 研究室PCで用意する引渡し表示

Codexの各作業終了時と、プログラムの公開状態表示には、次の項目を載せる。実装時に本書の操作手順を実コマンドへ更新する。

- 次の担当：ユーザー／Codex／プログラム。
- 現在の状態：準備中、起動準備完了、収集中、先頭1 QA確認完了、採点待ち、停止/失敗、解析完了。
- 次の操作：実コマンド、または貼るべき報告文ファイルの絶対パス。
- 固定CheckoutとRun、公開状態ファイル、最終更新、完了QA/予定QA、未試行・失敗・未知、停止理由。
- 収集完了と科学的な採否・採点完了の区別。exit 0だけで実験全体を成功と表示しない。

公開状態と `report_to_codex.txt` は、LLMを呼ばずに保存済み状態と実プロセスから作る。内部F/判断/候補段階/Goldの本文を含めない。
先頭1 QA完了時には全Main完了用の採点依頼を出さず、続行用の次操作を表示する。未完了・失敗なら停止報告用の文を出す。
ユーザーがコマンドやパスを毎回組み立て直す必要がないよう、実装後の報告文には実在する値を自動で入れる。
